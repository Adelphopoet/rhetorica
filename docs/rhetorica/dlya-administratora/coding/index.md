# Разработка dbt через Coding

Coding использует существующие профили агентов, GitLab/LLM/database-коннекторы и workspace skills. Отдельно вводить credentials для разработки не требуется.

## Настройка

1. Выберите в workspace доступные GitLab-коннектор, проект, целевую ветку и точный каталог dbt-проекта. Для многопроектного репозитория это, например, `dbt_dg/trino`.
2. Укажите нужный Trino-коннектор явно. Все выбранные профили должны иметь доступ к нему и GitLab-проекту.
3. Настройте координатору allowlist специалистов и соберите команду coding-агентов (см. ниже).
4. Выберите Coding environment с закреплённым образом. Дополнительные Python-зависимости задаются точными версиями в профиле среды.
5. Сохраните workspace defaults с координатором и командой. Они подставляют ресурсы в новый чат, но не выдают новых прав.

Пользователь включает Coding, обсуждает задачу и подтверждает актуальный план. Принятый run продолжает работу после закрытия чата. В журнале видны поручения координатора, сообщения и инструменты участников, результаты проверок и причина завершения.

## Команды coding-агентов

Системный администратор настраивает команды в разделе «Управление» → «Команды coding-агентов». Команда состоит из координатора и одного или нескольких участников. Для каждого участника задаются:

- имя в журнале, например «Data engineer» или «Reviewer»;
- существующий профиль агента;
- возможность: «Создаёт изменения» (candidate) или «Независимая проверка» (review);
- инструкция поручения;
- версии skills из тех, что уже разрешены профилю. Если версии не выбраны, участник получает активные skills своего профиля.

Координатор получает только инструменты вызова участников из своей команды. Он сам решает, кого вызвать, в каком порядке и нужно ли вернуть замечания проверяющего разработчику. Сервер не задаёт последовательность ролей. Сервер отвечает за бюджеты, сроки, права и допуск к публикации.

**Команда не выдаёт прав.** Участник использует только свои разрешения на GitLab, DWH и skills, а координатор — свою политику делегирования. Если участнику не хватает разрешения, сохранение или активация отклоняется. В сообщении указано имя участника и причина, а активная ревизия не меняется. Проверка повторяется при каждом запуске и перед каждым вызовом участника. Если разрешение отозвали во время работы, run завершается с причиной без публикации.

В чате команду можно выбрать прямо в селекторе агента, в группе «Команды». Разговор идёт с координатором команды, режим Coding включается сам, а подтверждённый план запускается с этой командой. Если выбрать самого координатора и включить Coding, используется команда из пресета workspace; если пресет указывает команду другого координатора, а у выбранного одна доступная команда, используется она.

Каждое изменение сохраняется новой ревизией. Её можно активировать сразу или позже из истории ревизий. Coding-пресет workspace выбирает команду, и каждый новый run сохраняет снимок ревизии, активной в момент запуска. Активация новой ревизии не меняет уже начатые run.

Возможность участника, а не его имя, определяет границу инструментов. Участник с возможностью candidate работает в собственной копии репозитория и сохраняет неизменяемый candidate. Проверяющий получает тот же candidate в отдельной песочнице и не может его менять. Вердикт каждого проверяющего становится обязательной проверкой candidate: публикация возможна, только если все проверки последнего candidate пройдены.

Координатор завершает работу решением «публиковать» или «остановить» с кратким итогом. Решение «остановить», запрос публикации без проверенного candidate, исчерпание бюджета, истечение срока и отзыв разрешения заканчиваются явной причиной и частичным результатом.

При обновлении существующие пресеты с координатором, Developer и QA переносятся в активную команду «Default coding team». Поведение таких workspace не меняется, пока администратор не отредактирует команду. Шаги `coding_task` в сценариях по-прежнему выбирают Developer и QA напрямую.

## Проверки dbt

Доступны `parse`, `list`, `compile`, `show` и `data_test`. Указывайте selector изменённой модели. `list` возвращает JSON metadata: путь, описание, колонки и effective config. Selector без выбранных узлов завершает проверку ошибкой, а не ложным `passed`. `show` проверяет SQL candidate, а `data_test` проверяет существующие production relations. Материализация через `run`, `build`, `seed` и `snapshot` не выполняется и обозначается `not_run`.

Для compile можно отключить introspection и заполнение relation cache. У `show` introspection остаётся включённой. Неподдерживаемые сочетания флагов отклоняются до запуска команды с исправимой ошибкой аргументов.

Сначала проверяйте причину ошибки: отсутствие доступа, недоступность DWH, ошибка SQL и исчерпание бюджета требуют разных действий. При недоступном DWH агент должен показать `blocked`/ошибку, а не утверждать, что проверка прошла.

## Бюджет и восстановление

Все вызовы модели специалистов и ручного компактирования расходуют общий принятый лимит разработки. Обсуждение плана использует обычный лимит чата. Фактические provider input/output/cache tokens обеих стадий увеличивают счётчики исходного разговора.

Большие результаты инструментов сохраняются полностью, но в контекст модели входят ограниченные представления с возможностью дочитать точный результат. Старые выводы сокращаются в представлении контекста; preview сохраняет начало и конец содержимого. Для коннектора с подтверждённой поддержкой нескольких tool calls включите `runtime_parallel_tool_calls` в extra settings: независимые чтения смогут использовать один ответ модели. Coding SDK исполняет сами инструменты последовательно. Порог нативного компактирования берётся из LLM-коннектора; в этом режиме второй ручной компактор не запускается.

После перезапуска worker использует сохранённую историю и результаты. Повтор сохранённого ответа не увеличивает токены и итерации. При потере локальной рабочей копии восстанавливаются сохранённый snapshot либо подтверждённые патчи.

## Публикация

Без разрешения на публикацию успешный run возвращает candidate и QA-report с `publication_not_authorized`. Для Draft MR нужны отдельные write scopes и delegation grant; один allowlist специалистов не даёт права записи. Ошибки обязательных проверок блокируют публикацию.

Локальный Docker предназначен для проверки доверенных репозиториев. Приёмка production Kubernetes runtime выполняется отдельно.
