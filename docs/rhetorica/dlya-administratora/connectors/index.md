# Коннекторы

Коннекторы настраиваются в административной консоли и принадлежат workspace. Доступный набор включает DWH, LLM, RAG, документацию, GitLab, Airflow, Kubernetes, VictoriaMetrics, Mattermost и MCP. Jira, Confluence и каталоги метаданных подключаются как стандартные MCP-коннекторы.

## Минимальный порядок

1. Создайте конфигурацию с уникальным понятным именем.
2. Укажите назначение: какие задачи и данные покрывает источник.
3. Ограничьте проекты, namespace, сервисы или инструменты allowlist-ом, если тип коннектора это поддерживает.
4. Передайте секрет через настроенный secret backend. Не храните токен в Markdown, Git или описании коннектора.
5. Выполните health/sync-проверку и реальный read-only smoke test.
6. Добавьте коннектор только тем агентам, которым он нужен.

Флаг `has_secret` означает наличие ссылки на секрет, но не гарантирует, что текущий runtime способен получить значение. После изменения secret backend проверяйте API и worker отдельно.

## Настройки LLM

В форме LLM-коннектора доступны модель, URL и endpoint, проверка TLS, ключи API, параметры генерации, HTTP-заголовки и дополнительные настройки.

- `Temperature`: от 0 до 2; пустое поле оставляет выбор провайдеру.
- `Top P`: от 0 до 1, включая 0; пустое поле сохраняется как `null`, параметр не включается в запрос провайдеру. У существующих коннекторов миграция оставляет поле пустым.
- `Max response tokens`: лимит генерации или пустое поле для значения провайдера. Для Chat Completions отдельно выбирается имя параметра: `max_tokens` или `max_completion_tokens`.
- `Context window` и `Require final answer tool` управляются отдельными полями.
- `HTTP headers JSON`: объект с текстовыми значениями. Учётные данные следует вводить в поля API keys.
- `Additional LLM settings JSON`: остальные настройки коннектора, например `chat_template_enable_thinking`, `structured_output_enabled`, `llm_retry_attempts`, `responses_endpoint_path`. Поддерживаются значения типов string, number и boolean. Удаление ключа из объекта удаляет настройку при сохранении. Этот объект не является произвольным телом запроса: на выполнение влияют только опции, поддержанные backend.

При повторном сохранении сохраняются пустые параметры генерации, заголовки, дополнительные настройки и выбранные существующие ключи. Значения сохранённых API keys скрыты; форма показывает количество и позволяет сохранить, удалить или добавить ключи. В `Connector details` доступны ID, workspace, даты создания и изменения, а также профиль возможностей, если API его возвращает.

Устаревшее поле API `phase_capable` принимает только `null`: фазовые overrides не поддерживаются и отклоняются при валидации.

## Несколько MCP одного типа

Каждый MCP-коннектор показывается агенту как отдельный инстанс. Это важно, если подключены, например, две Jira с одинаковыми методами:

- задайте каждому коннектору уникальное понятное `name`;
- в `usage_description` явно укажите организацию, контур или назначение инстанса;
- настройте agent connector allowlist и `allowed_tool_names` независимо для каждого инстанса.

Переключатель `Expose through external MCP` управляет публикацией всего MCP-коннектора на `/mcp`. Выключите его, если коннектор должен оставаться доступным внутренним агентам, но не внешним MCP-клиентам. Для новых коннекторов публикация выключена по умолчанию; после включения наружу попадают только методы, разрешённые через `allowed_tool_names`.

LLM сама выбирает конкретный коннектор, просматривает его каталог и загружает схемы только нужных tools. Backend не ранжирует похожие коннекторы, не делает fuzzy matching и не подменяет выбранный инстанс. Если описаний недостаточно для безопасного выбора, агент должен запросить уточнение.

## Отложенная загрузка tool-групп

Обычные tools не передаются LLM полным списком на каждом ходе. Модель сразу видит компактный каталог активных групп (`name` и `description`), затем сама загружает одну или несколько разрешённых capability-групп по точному имени.

- группа появляется только при наличии хотя бы одного активного разрешённого tool;
- отключённые коннекторы и запрещённые агенту группы в каталог не попадают;
- пустые connector sections не передаются модели;
- backend не выбирает группу по тексту вопроса и не применяет ranking или fuzzy matching;
- крупные surfaces разделены на небольшие стабильные namespaces.
- каталог workspace skills (`name` и `use_when`) и `read_workspace_skill` доступны сразу, потому что это обязательный control-plane routing до domain tools;
- каталоги групп и MCP tools передаются модели inline с точными именами; raw artifact handle используется только для аудита и не заменяет каталог.
- явно загруженные группы и MCP tools сохраняются в рамках чата; на каждом новом ходе schemas восстанавливаются только через актуальные allowlists и каталоги;
- модель может явно выгрузить группу или MCP tools; автоматического routing по теме, TTL или ключевым словам нет.

Поэтому `name`, `usage_description`, allowlists и видимость коннектора должны точно описывать доступный runtime. Jira, Confluence и каталог метаданных остаются самостоятельными MCP-инстансами в общей connector surface.
