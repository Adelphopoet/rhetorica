# Агенты и workspace skills

Агент — это управляемый профиль с инструкцией, моделью и явным набором доступных коннекторов. Пользователь выбирает агента по задаче; runtime не должен расширять его права догадкой.

## Перед публикацией агента

- сформулируйте назначение и границы ответственности;
- оставьте только необходимые инструменты и источники;
- проверьте успешный сценарий и отказ при недоступном источнике;
- убедитесь, что ответ показывает evidence и предупреждения;
- не помещайте секреты в system prompt или skill.

Workspace skill хранит повторяемую инструкцию и может быть видим стандартному ассистенту или только выбранным агентам. Навык должен описывать проверяемый процесс, а не давать неограниченное разрешение на внешние действия.

## Политики coding

Опасные права публикации GitLab сохраняются отдельно от имени, prompt и обычных
allowlist агента. Редактор доступен только системному администратору. Новая и
мигрированная policy закрыта по умолчанию: пустой список scope запрещает публикацию.

Для прямой публикации укажите точный GitLab-коннектор, project path или ID, ветки и
относительные POSIX-пути. `default_project_paths` коннектора помогает поиску, но не
является разрешением на запись. Absolute paths, traversal, `.git`, NUL и обратные
слеши отклоняются.

Delegation состоит из двух независимых настроек:

1. Добавьте активного агента того же workspace в список разрешённых субагентов.
2. Создайте для него явный grant с собственными GitLab scopes.

Один только выбор субагента права публикации не выдаёт. Итоговый delegated scope
всегда уже пересечения grant родителя, direct scope дочернего агента, принятого при
старте snapshot и scope конкретного запуска. Direct scope родителя дочернему агенту
не наследуется.

`Max iterations` и `Max runtime` задают верхние границы. Runtime и профиль среды
могут только уменьшить их. Фактическое соблюдение budget относится к coding runner;
сохранение policy само по себе ничего не запускает и не обращается к GitLab.

Каждое сохранение использует revision. Если другая вкладка уже сохранила изменения,
сервер отвечает `409 policy_revision_conflict`. Редактор оставляет локальный черновик
открытым и предлагает явно загрузить актуальную policy; автоматического merge или
retry нет, чтобы старая вкладка не восстановила отозванный grant.

Для безопасного отзыва сначала удалите grant или direct scope и сохраните policy.
Следующая внешняя операция обязана повторно проверить актуальные policy, membership
и доступность resource. Расширение policy действует только для новых запусков, а
отзыв сужает уже принятый snapshot. Удаление GitLab token или resource grant выполняйте
после сохранения запрета; при частичном инциденте сам revoke ресурса также приводит к
fail-closed отказу.
