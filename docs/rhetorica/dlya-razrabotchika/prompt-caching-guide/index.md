# Prompt caching в LLM-агентах: практический гайд

Технология [Prompt Caching](https://habr.com/ru/articles/978498/) сохраняет уже вычисленные префиксы промптов в памяти провайдера, что снижает расходы на входные токены на 50–90% и ускоряет ответы LLM-агентов

> **Главный принцип: оптимизируйте не процент попаданий в кеш, а стоимость успешно выполненной задачи.** Для этого сохраняйте полезный префикс контекста стабильным, контролируйте его рост и проверяйте качество после каждого изменения.

## 1. Что именно кешируется

Prompt caching повторно использует вычисления для уже обработанного начала запроса — **префикса**. Это не кеш готовых ответов: модель по-прежнему генерирует продолжение. В этой статье рассматривается именно кеширование контекста на стороне провайдера или inference-сервера, а не возврат старого ответа из Redis по похожему вопросу.

Обычно выигрыш связан с обработкой входа (*prefill*), поэтому кеширование особенно полезно при длинных повторяющихся инструкциях и истории. Оно не устраняет время выполнения SQL/MCP и не делает генерацию длинного ответа бесплатной. Устройство prefix/KV cache описано в [документации vLLM](https://docs.vllm.ai/en/latest/design/prefix_caching/) и [обзоре LangChain](https://www.langchain.com/blog/deep-agents-prompt-caching).

Пример двух запросов:

```text
Запрос 1: [общие инструкции][tools][контекст проекта][вопрос A]
Запрос 2: [общие инструкции][tools][контекст проекта][вопрос B]
          └──────────────── общий префикс ────────────────┘
```

Одинаковый текст в середине разных префиксов сам по себе не означает cache hit. Кроме совпадения, важны доступные границы кеширования, минимальная длина, совместимые настройки модели и наличие записи в кеше. Повтор одинакового запроса тоже не является универсальной гарантией попадания: например, DeepSeek прямо описывает кеш как best effort. См. [DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/).

**Практический вывод:** начните с того, как harness собирает запрос, а не с добавления отдельного кеширующего сервиса.

### Стабильный credential как условие измерения

Если один connector обслуживается несколькими API keys, случайный выбор ключа на
каждом сообщении может отправить одинаковый префикс на разные inference-инстансы
или маршруты провайдера. Поэтому Rhetorica закрепляет позицию ключа за парой
`conversation + connector` в PostgreSQL, а raw key получает только в памяти
текущего хода через существующий `SecretStore`. Это повышает воспроизводимость и
может увеличить prompt-cache reuse, но не гарантирует конкретный hit rate: его
определяет провайдер вместе с точным префиксом, TTL, моделью и маршрутизацией.

При retryable ошибке отдельного model call runtime пробует следующий доступный
ключ. После успешной попытки binding обновляется, поэтому последующие вызовы
этого разговора используют новый ключ. Если набор ключей изменился, старая
позиция признаётся устаревшей и выбирается заново; прямое изменение секрета вне
поддерживаемого connector API системой не обнаруживается автоматически.

## 2. Разделите контекст по сроку жизни

Полезный ориентир из [практики Claude Code](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything) — размещать более стабильные части раньше, а изменяющиеся позже.

Для вашего приложения предлагается такая логическая структура:

| Слой | Что хранить | Когда обновлять |
|---|---|---|
| Общий | Правила поведения, базовые инструменты, общие соглашения | При выпуске версии агента |
| Проектный | Правила работы с конкретным workspace, соглашения репозитория | При смене проекта или версии конфигурации |
| Сессионный | Исходные условия задачи, загруженные материалы | При старте или контролируемом пересоздании контекста |
| История | Сообщения, вызовы tools, зафиксированные результаты | Добавлять новые элементы в конец |
| Текущий | Новый вопрос, изменение состояния, свежие результаты | На текущем шаге |

Это **логические слои, а не универсальный порядок полей JSON**: фактический промпт строит сервер API. Не переносите инструкции между ролями только ради кеша и не превращайте найденный документ в системную инструкцию. Разбор преобразования запроса в контекст есть в [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/).

Для общих инструкций заведите `prompt_version`; для набора инструментов — `toolset_version`; для проектных правил — `workspace_context_version`. При обычном релизе можно сохранять старый снимок для начатых сессий. Исправления безопасности и отзыв доступа должны применяться немедленно, даже ценой cache miss.

## 3. Сделайте сборку запроса детерминированной

Одинаковая конфигурация должна давать одинаковые инструкции и определения tools. В статье о Codex описана реальная проблема: непостоянный порядок MCP-инструментов приводил к промахам кеша. См. раздел **Performance considerations** в [разборе Codex](https://openai.com/index/unrolling-the-codex-agent-loop/).

Для harness предлагаются следующие правила.

**Фиксируйте порядок инструментов.** Соберите результаты discovery от MCP-серверов, отсортируйте по устойчивому полному имени, проверьте уникальность и сохраните снимок. Не формируйте `tools` в порядке завершения параллельных сетевых вызовов.

**Не генерируйте схемы заново на каждом шаге.** Изменение описания, списка доступных агентов, примеров или порядка полей должно быть контролируемым изменением версии. При сериализации собственных объектов используйте единые правила. Не переупорядочивайте историю, массивы аргументов и непрозрачные блоки, полученные от модели.

**Уберите служебный шум из модельного контекста.** `request_id`, trace ID, время начала HTTP-запроса и адрес воркера оставьте в логах, если они не нужны для решения задачи. Полезную динамику — смену бизнес-даты, рабочей директории или состояния задачи — передавайте новым событием в допустимой для конкретного API форме.

Плохой шаблон:

```text
SYSTEM: Сейчас {datetime.now()}, request_id={uuid4()}.
        Далее 20 000 токенов правил и описаний инструментов...
```

Предлагаемый вариант:

```text
СТАБИЛЬНАЯ ЧАСТЬ: правила и определения инструментов.
ИСТОРИЯ: ранее отправленные сообщения без изменений.
НОВОЕ СОБЫТИЕ: значимое изменение состояния, только когда оно произошло.
```

Сравнивайте данные **после всех middleware и адаптеров**, максимально близко к отправке. Стабильный шаблон ничего не доказывает, если следующий слой незаметно добавляет timestamp.

## 4. Управляйте большим каталогом tools/MCP

Не сводите решение к выбору между «всегда отправлять все инструменты» и «каждый шаг заново выбирать список». Для собственного приложения стоит проверить три стратегии.

### Стабильный набор для сценария

На входе в задачу выберите профиль: аналитика данных, работа с кодом, сопровождение платформы. Зафиксируйте небольшой набор инструментов на время выполнения.

Это разумная стартовая реализация без специальной поддержки API. Цена решения — возможная перезагрузка контекста при переходе в другой профиль. Измеряйте, насколько часто такой переход действительно нужен.

### Нативная отложенная загрузка

При поддержке провайдером используйте tool search/deferred loading. В Claude найденное определение добавляется в историю через `tool_reference`, а не переписывает начальный префикс. В OpenAI tool search также загружает определения в конец контекста; для расширенных сценариев документирован `additional_tools`, позицию которого нужно сохранять при повторной отправке истории.

Источники: [Claude: Tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching), [OpenAI: Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search). Архитектурное объяснение — [Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use).

**Нативный deferred loading и произвольное изменение обычного массива `tools` — разные механизмы.** Совместимый формат API не гарантирует поддержку обоих.

### Поиск и диспетчеризация средствами harness

Для endpoint без подходящего нативного механизма можно экспериментально оставить стабильные интерфейсы:

```text
search_tools(query) → разрешённые инструменты и их схемы
invoke_tool(tool_id, arguments) → результат конкретного инструмента
```

Это проектный компромисс: определение находится в результате поиска, а не в нативной схеме вызываемой функции. Поэтому возможны дополнительные шаги и ошибки аргументов. Сравните подход со стабильными профилями на ваших задачах.

Диспетчер обязан проверять текущие права, валидировать аргументы по реальной схеме и соблюдать подтверждения для изменяющих операций. Не превращайте его в выполнение произвольного кода. **Кешируемость не заменяет авторизацию.**

Отдельно тестируйте переключение `tool_choice`, режима reasoning и формата ответа: их влияние на кеш отличается между API. Для Claude это перечислено в [таблице инвалидации](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching).

## 5. Храните историю как журнал, а не пересобираемый документ

Предлагаемый инвариант между точками compaction:

```text
history[n + 1] = history[n] + новые события
```

«Динамический результат инструмента» не означает «всегда некешируемый». Результат SQL появился только сейчас, но после первой отправки может оставаться неизменной частью следующих запросов. Проблема возникает, когда приложение заново выполняет запрос, перерисовывает таблицу или подменяет старый результат при каждом сборе истории.

Для coding-агента особенно важно разделять историю наблюдений и текущее состояние файлов. В Claude Code изменение файла не подменяет прежнее чтение: добавляется уведомление, после чего файл можно перечитать. Этот подход описан в [How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching).

В собственной реализации храните отдельно исходный результат, модельное представление, версию артефакта и отображение для UI. Косметическое изменение интерфейса не должно менять ранее отправленное модели содержимое. Новое чтение файла или повторный SQL — новое событие с новой версией результата.

Фиксируйте завершённые модельные события; промежуточные streaming-дельты оставляйте в транспортном слое и UI. Не восстанавливайте историю только по видимым сообщениям чата: API может требовать tool-call IDs и специальные reasoning/thinking-блоки. Сохраняйте и возвращайте такие элементы по контракту провайдера, не редактируя их содержимое.

`previous_response_id` — отдельный механизм управления состоянием, а не обещание бесплатной истории. OpenAI явно указывает, что предыдущие входные токены цепочки продолжают учитываться в тарификации. См. [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state).

## 6. Ограничивайте результаты до добавления в историю

Большой вывод инструмента лучше обработать **до первой отправки модели**, чем многократно обрезать уже отправленный текст. Использование файлов как внешнего контекста разобрано в [статье Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).

Для аналитического ассистента предлагается формат наблюдения:

```json
{
  "artifact_id": "query-result-42",
  "artifact_version": 1,
  "row_count": 183427,
  "preview_rows": 20,
  "truncated": true,
  "columns": ["event_date", "revenue"],
  "next_action": "read_artifact или новый агрегирующий SQL"
}
```

Полные данные остаются в артефакте; в контекст попадают схема, небольшой фрагмент и существенная для задачи информация. Для кода аналогичный интерфейс — чтение диапазона строк, поиск символа, diff, хвост лога.

Размер preview — настройка, которую нужно подобрать, а не универсальное число. Для каждой задачи проверяйте, хватает ли данных для вывода. Агент должен явно видеть, что результат усечён; нельзя делать вывод обо всей таблице по нескольким строкам без дополнительной проверки.

Ссылка должна вести на конкретную версию результата и проверять доступ при чтении. Полезные даты данных сохраняйте: удалять `as_of_date` ради стабильности опаснее, чем потерять кеш.

## 7. Делайте compaction контролируемой сменой контекста

Compaction — сокращение истории с сохранением необходимого состояния задачи. Переписывание ранних сообщений меняет префикс, но сохранение всей истории бесконечно тоже не является оптимизацией. Компромисс между сокращением контекста и сохранением кеша исследуется в [TokenPilot](https://arxiv.org/abs/2606.17016).

Для harness предлагается понятие **эпохи контекста**: внутри эпохи история только дополняется; compaction создаёт новую эпоху. Стабильные общие инструкции сохраняются, а выбранный участок истории заменяется summary. Потеря повторного использования начинается в изменённой части, а не обязательно с самого начала запроса.

Не запускайте summary на каждом ходе. Используйте порог с запасом под следующий tool result, reasoning и ответ. Например, 75% окна как сигнал и 45% как целевой объём после сжатия — возможная начальная гипотеза для теста, **не рекомендация провайдера**. Важнее бюджет в токенах и измеренная устойчивость задачи.

В summary стоит сохранять цель, ограничения, проверенные факты с источниками, принятые решения, значимые ошибки, идентификаторы файлов/результатов и незавершённые действия. Не оставляйте вызов инструмента без связанного результата. Права и разрешения после compaction проверяются заново, а не наследуются из текстового summary.

### Не делайте само сжатие неоправданно дорогим

Команда Claude Code описывает *cache-safe fork*: запрос на summary использует тот же префикс и историю, а инструкция на сжатие добавляется в конец. Так можно повторно использовать родительский кеш. Для этого нужен резерв окна; после замены истории новым summary изменённая часть всё равно потребует прогрева. См. [Lessons from building Claude Code](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything).

Реализация такого fork не должна выполнять побочные действия: блокируйте их в execution layer. Сравните его стоимость с отдельной дешёвой моделью — холодный кеш другой модели может перевесить низкую цену токенов.

Обязательно тестируйте возобновление после простоя. В [постмортеме Anthropic](https://www.anthropic.com/engineering/april-23-postmortem) описан баг, при котором однократная очистка thinking повторялась на каждом ходе, ухудшая и память агента, и кеширование.

## 8. Вынесите особенности провайдеров в адаптеры

Не делайте один глобальный флаг `enable_cache=True` для всех endpoint. Заведите проверяемый профиль возможностей для сочетания **провайдер + endpoint + модель + версия адаптера**.

| Площадка | Что учитывать | Документация |
|---|---|---|
| OpenAI | У GPT-5.6 и более новых моделей документированы implicit/explicit режимы, `prompt_cache_options`, `prompt_cache_breakpoint` и отдельная тарификация записи. У более ранних моделей правила отличаются. | [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) |
| Claude API | `cache_control`, автоматическое размещение или явные границы; TTL 5 минут или 1 час. Минимальная длина и отдельные особенности зависят от модели. | [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) |
| DeepSeek, прямой API | Кеширование включено автоматически; попадания best effort, построение кеша не мгновенное. | [Context Caching](https://api-docs.deepseek.com/guides/kv_cache/) |
| Alibaba Cloud Model Studio | Explicit и implicit cache; доступность зависит от модели, региона и способа вызова. | [Qwen Context Cache](https://www.alibabacloud.com/help/en/model-studio/context-cache) |

Для Yandex Cloud и других совместимых площадок не переносите параметры прямого API модели без проверки. Поддержку конкретных полей, тарифов и TTL следует подтвердить документацией endpoint и интеграционным тестом. Совместимость с Responses API сама по себе этого не доказывает.

**Явная граница кеширования обозначает конец префикса, а не независимый фрагмент.** В Claude доступны до четырёх границ и ограниченное окно поиска предыдущих записей. Поэтому недостаточно каждый раз ставить маркер только после изменяющегося хвоста: полезно иметь сохранённую границу после стабильной части. См. [правила размещения breakpoints](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

`prompt_cache_key` не заменяет совпадение контекста. У современных OpenAI-моделей он используется для раздельного учёта кеша; у более ранних помогал маршрутизации. Не генерируйте случайный ключ на каждый запрос. Группировку согласуйте с изоляцией клиентов. См. [Prompt cache keys](https://developers.openai.com/api/docs/guides/prompt-caching).

TTL выбирайте по паузам между вызовами и цене записи. Не запускайте постоянные запросы «для поддержания тепла» без расчёта: прогрев может стоить дороже редких промахов. Для self-hosted serving отдельно проверьте изоляцию кеша; vLLM, например, документирует `cache_salt` для разделения групп доверия в [Automatic Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/).

Кеширование не меняет требований к доступу и конфиденциальности. Отдельно проверяйте допустимость передачи данных провайдеру, регион обработки и режим хранения. TTL вычислительного кеша не равен сроку хранения сообщений вашего приложения.

## 9. Считайте реальную стоимость

Нормализуйте учёт входа в три непересекающиеся категории:

```text
U — обычные входные токены
R — токены, прочитанные из кеша
W — токены, записанные в кеш

input_total = U + R + W
input_cost = (U × price_input + R × price_read + W × price_write) / 1_000_000
```

Это внутренняя модель учёта, а не универсальная структура API. Если записи тарифицируются как обычный вход, задайте соответствующую цену; не добавляйте к цене записи обычную цену второй раз. При разных TTL разделяйте `W` по тарифам. Текущие правила: [OpenAI Pricing](https://developers.openai.com/api/docs/pricing), [Claude Pricing](https://platform.claude.com/docs/en/about-claude/pricing).

**Условный пример, не тариф конкретной модели.** Есть десять вызовов, каждый с общим префиксом 20 000 токенов и непереиспользуемым хвостом 2 000. Запись префикса стоит 1,25 обычной цены, чтение — 0,1. Префикс записывается один раз; все девять следующих чтений успешны; хвост не записывается.

```text
Без кеша: 10 × 22 000 = 220 000 условных единиц.
С кешем: 20 000 × 1,25 + 9 × 20 000 × 0,1 + 10 × 2 000 = 63 000.
Экономия на входе: около 71%.
```

Это не 71% экономии всей задачи: остаются output, вызовы tools, sandbox, retries и summary. В реальном агентном цикле история растёт, а вчерашний хвост может повторно использоваться. Поэтому расчёт нужно повторить по фактическим трассам.

Для compaction применима инженерная эвристика: ожидаемая экономия на оставшихся шагах должна превышать цену summary и повторного прогрева. Но даже выгодное сжатие отклоняется, если оно ухудшает выполнение задачи.

## 10. Добавьте наблюдаемость

Для каждого LLM-вызова предлагается сохранять нормализованный usage, стоимость и длительности, а также `provider`, `model`, `prompt_version`, `toolset_version`, `context_epoch`, причину compaction и интервал от предыдущего вызова. Отдельно учитывайте ретраи и обращения subagents.

Нормализация принципиальна: в Claude `input_tokens` не включает cache reads/writes; полный вход получается их суммой. В OpenAI Responses детали кеша входят в общий `input_tokens`. Не вычисляйте одну метрику одинаковой формулой по ненормализованным ответам. См. [Claude usage](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) и [OpenAI usage](https://developers.openai.com/api/docs/guides/prompt-caching).

Минимальные метрики для вашего приложения:

| Метрика | Зачем |
|---|---|
| `sum(cache_read_tokens) / sum(input_tokens_total)` | Доля входных токенов, прочитанных из кеша; не среднее процентов отдельных вызовов |
| Стоимость на успешную задачу | Суммарные расходы когорты, включая неуспехи, делённые на число успешных задач |
| p50/p95 TTFT и полного времени задачи | Отделить ускорение модели от SQL, tools и очередей |
| Task success, число шагов и повторных tool calls | Найти деградацию, скрытую за экономией токенов |
| Распределение причин смены префикса | Отличить случайные изменения от compaction, новой модели или прав доступа |

Отсутствующее поле cache usage — **«неизвестно», а не ноль**. Храните исходный usage в защищённой диагностике, чтобы менять нормализатор без потери данных.

Для поддерживаемых OpenAI-моделей есть [Prompt cache diagnostics](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics): `comparison_response_id` задаёт предыдущий ответ для сравнения; результат объясняет изменения tools, input или настроек. Это диагностика, не загрузка истории и не управление попаданием.

В собственных логах достаточно версий, размеров и защищённых отпечатков частей запроса. Не записывайте полный промпт с SQL-результатами и персональными данными в общедоступную телеметрию. При одинаковом клиентском отпечатке провайдер всё ещё может вернуть miss: локальный hash не доказывает совпадение серверного представления.

## 11. Проверьте оптимизацию экспериментом

Предлагается разделить два вида проверки.

**Контрактные тесты без модели** проверяют детерминированность и целостность: другой порядок ответов MCP даёт тот же snapshot; restart воркера не меняет историю; редактирование UI не меняет модельный payload; tool-call IDs и связанные результаты сохранены; отзыв прав действительно блокирует исполнение.

**Интеграционные тесты с моделью** проверяют кеш и результат задачи. Нужны холодный старт, несколько продолжений, пауза за пределами TTL, крупный tool result, compaction, смена модели и релиз toolset. Сравните старый и новый harness на одинаковых сценариях поиска данных, text-to-SQL, разбора DAG и изменения кода.

Фиксируйте версию модели и настройки. Для воспроизводимых replay используйте записанные безопасные результаты tools; отдельно проводите live-проверку. Повторите сценарии: один удачный cache hit недостаточен. Не позволяйте прогреву варианта A незаметно улучшать вариант B — разделяйте пространства кеша, когда API это поддерживает, либо явно учитывайте общий прогрев.

Нет универсального требования «cache hit rate должен быть 90%». Агент, получающий много новых полезных данных, закономерно читает меньше из кеша. Сравнивайте одинаковые классы задач. Исследовательский пример оценки нескольких стратегий — [Don’t Break the Cache](https://arxiv.org/abs/2601.06007); его результаты не следует переносить на ваше приложение без измерений.

## 12. Порядок внедрения

| Приоритет | Изменение | Критерий готовности |
|---|---|---|
| P0 | Нормализованный usage и baseline стоимости/качества | Видна стоимость каждого вызова и всей задачи |
| P0 | Версионированные snapshots промпта и toolset | Тесты подтверждают детерминированность сборки |
| P0 | Неизменяемое модельное представление истории | Новые события не переписывают старые |
| P1 | Ограничение tool output до включения в историю | Большие данные доступны через версионированные артефакты |
| P1 | Профили tools или нативный deferred loading | Стоимость снизилась без ухудшения выбора инструментов |
| P1 | Compaction с бюджетом и отдельными тестами | Агент сохраняет факты, состояние и незавершённую работу |
| P2 | Настройка TTL, ключей, fork и прогрева | Выгода подтверждена на реальных паузах и нагрузке |

**Не начинайте с удаления полезной истории или агрессивного урезания tool descriptions. Сначала устраните случайные изменения префикса и ошибки измерения; затем оптимизируйте объём контекста и стратегию выполнения.**
