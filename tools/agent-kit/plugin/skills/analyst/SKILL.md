# Аналитик поверх Rhetorica

Rhetorica — это руки: `list_metadata_services` показывает database services OpenMetadata, `search_tables` ищет таблицы в metadata и runtime-каталогах, `run_sql` выполняет read-only SQL под сервисной учёткой workspace, `list_connectors` показывает базы. Думать, писать SQL и держать знания — твоя работа.

Все tools лежат на MCP-сервере `rhetorica`. Агентские tools (`ask_chat`, `list_agents`, `*_conversation*`) не использовать: ответ идёт минутами и не нужен, когда SQL пишешь сам.

## Шаг 0. База знаний

База — папка с `knowledge/` и `reports/`. Найти в таком порядке:

1. переменная окружения `ANALYTICS_KB`;
2. `~/analytics-kb/`;
3. ничего нет → спросить один раз: «Куда складывать базу знаний: (а) `~/analytics-kb`, (б) папка текущего проекта `./analytics-kb`, (в) свой путь, например волт Obsidian». Создать по [references/knowledge-base.md](references/knowledge-base.md) и сказать, как закрепить выбор через `ANALYTICS_KB`.

Перед ответом прочитать `knowledge/tables.md` и `knowledge/sql-library.md` целиком, если они короче 300 строк, иначе поискать по ключевым словам вопроса. Если таблица уже описана, а запрос похожий уже есть, начинать с них, а не с поиска.

## Шаг 1. Найти таблицу

1. Вызвать `list_connectors`. Если OpenMetadata service ещё не известен из вопроса или базы знаний, вызвать `list_metadata_services`. `service_name` и `connector_name` — разные идентификаторы; не связывать их по одному совпадению типа движка. Если проверенной связи нет и вариантов несколько, спросить человека, в каком connector выполнять SQL.
2. `search_tables(query=<вопрос или ключевые слова>, service_name=<точное имя OMD>, connector_name=<точное имя runtime-коннектора>)`. Неизвестный аргумент опустить; если известна схема, добавить `database`.
3. В `tried` смотреть `status`, ошибку и число найденных. `failed` означает недоступный источник, а не отсутствие таблиц. У кандидатов различать `origin`, `service` и `connector`, затем смотреть `found_by`, `layer`, `suspicious`, `description`. Одноимённые кандидаты из разных sources — разные таблицы.
4. Колонки: выполнять `run_sql` только через явно выбранный или уже проверенный в базе знаний `connector_name`. Для ClickHouse — `DESCRIBE <schema.table>`, для остальных — `information_schema.columns`. Описания колонок в ClickHouse лежат в комментариях, читать их.
5. Свежесть: `SELECT min(<дата>), max(<дата>), count() FROM <таблица>` с фильтром на последние дни, если таблица большая.

Успешно пусто на всех ступенях → сказать, что искали, предложить другие слова и спросить имя таблицы. Есть `failed` → отдельно сказать, какой источник недоступен; не выдавать это за «таблицы нет». Не гадать имена.

## Шаг 2. SQL

Правила в [references/sql-rules.md](references/sql-rules.md). Кратко: только чтение, явный `LIMIT`, фильтр по дате и партиции, без `SELECT *`, сначала проверить на коротком периоде, потом считать за нужный.

## Шаг 3. Ответ

Формат в [references/report-format.md](references/report-format.md): «Ответ, Интерпретация, SQL, Источник». Число первым, потом контекст. Что не проверено, назвать явно.

## Шаг 4. Сохранить и дописать базу

После каждого исследования, не только по просьбе:

- `reports/<slug>/<slug>.md` по формату отчёта, графики рядом, `<slug>` = тема и период в kebab-case;
- `knowledge/tables.md`: новая таблица или новая деталь о старой (grain, ключ даты, подвох);
- `knowledge/sql-library.md`: финальный рабочий запрос с заголовком и датой;
- `knowledge/business-context.md`: если человек поправил термин, фильтр или интерпретацию.

Проверить, что файлы на месте (`ls reports/<slug>/`), и в ответе назвать путь к отчёту.
